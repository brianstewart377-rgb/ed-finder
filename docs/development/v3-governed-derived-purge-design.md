# Governed derived-generation purge path

**Status:** docs-only design record; no migration, operator action, workflow, production command, or production authority is created by this document.

**Decision record (owner, 2026-10-11):** the owner chose a governed purge of only the incomplete `ratings_v4_prod_p4` generation and the superseded, unpublished `ratings_v4_prod_p4_opt1` generation **before the Finder product builds**. This deliberately supersedes the 2026-10-10 instruction to defer any purge in the [ROADMAP capacity-decision sequence](../ROADMAP.md) and the original decision recorded in [Finder rollout — capacity decision (2026-10-10)](../operations/v3-finder-capacity-decision-2026-10-10.md). The decision retains the already-selected wide-row Finder design and attachment of both Finder products to the published generation.

The owner made this choice knowing that decisions A + B alone need about 152 GB for Search plus the wide-row archetype product and therefore leave about **140 GB of headroom from the dated 292 GB free-space measurement without any purge** (`docs/operations/v3-finder-capacity-decision-2026-10-10.md:173-192`). The owner also accepted that no repository-authorized PostgreSQL 18 restore, PITR, or disaster-recovery route exists. That acceptance is not a rollback mechanism; the execution gates, phase isolation, and stop conditions in this design remain mandatory (`docs/operations/infrastructure-status.md:73-79`).

The ROADMAP amendment in section 5 is a prerequisite, not optional documentation. The ROADMAP is the first programme authority and old evidence cannot override it (`CLAUDE.md:5-19`, `docs/operations/v3-finder-production-rollout-state.md:9-17`).

This is a design for a later reviewed implementation PR. It is not production authority. Production commands must be provided by a current V3 workflow/runbook with an explicit target and safety boundary (`CLAUDE.md:76-95`), and ordinary coding work may not read or write production (`CLAUDE.md:148-156`).

The repository pointer contract locates V3 migrations under `sql/v3/migrations/`, requires fail-closed validation/parameterized SQL/bounded inputs, and warns that adding a V3 migration triggers a production-promotion registration cascade (`AGENTS.md:26-32`). This design includes that cascade rather than treating a migration file alone as deployable.

### 1.4 Every deletion/update/truncation guard and its exact conditions

1. `v3_meta.guard_derived_manifest` rejects every deletion of a generation manifest; makes the generation identity/manifest immutable; permits only `BUILDING -> VALIDATING|FAILED`, `VALIDATING -> READY|FAILED`, `READY -> PUBLISHED`, `PUBLISHED -> RETIRED`, and `RETIRED -> PUBLISHED`; and seals source/content after `BUILDING` and validation after `VALIDATING` (`sql/v3/migrations/003_ratings_v4_derived.sql:41-69`). Its row trigger covers `UPDATE OR DELETE` (`sql/v3/migrations/003_ratings_v4_derived.sql:70-71`). Therefore `p4` and `opt1` can both be moved to `FAILED` without inventing a new lifecycle transition, while their manifests cannot be removed.

2. `v3_derived.guard_generation_write` rejects every `TRUNCATE`. For statement transition rows, it locks each referenced generation `FOR SHARE` and permits an insert, delete, or either side of an update only when the generation is exactly `BUILDING`; a missing generation also fails because its state is distinct from `BUILDING` (`sql/v3/migrations/003_ratings_v4_derived.sql:189-205`). Five statement triggers attach it to `build_chunk`, `system_rating_vector`, `body_mechanics`, and `economy_opportunity` (`sql/v3/migrations/003_ratings_v4_derived.sql:206-216`), and migration `004` initially attaches the same five forms to Search and every old derived-spatial/cluster relation (`sql/v3/migrations/004_v3_search_spatial_clusters.sql:153-169`). This means the current generic guard unexpectedly permits deletion from a `BUILDING` generation but not from `opt1` in `VALIDATING`; the purge migration must tighten that delete branch to explicit authorization rather than broaden it.

3. Migration `006` removes all five generic triggers from `system_search` (`sql/v3/migrations/006_v3_derived_product_lifecycle.sql:127-134`). `guard_system_search_insert` then permits inserts only when the base generation is `BUILDING`, `VALIDATING`, or `READY` and its `system_search` product is exactly `BUILDING` (`sql/v3/migrations/006_v3_derived_product_lifecycle.sql:136-163`). `reject_system_search_mutation` unconditionally rejects updates, deletes, and truncates of both `system_search` and `search_build_chunk`, including zero-row statements (`sql/v3/migrations/006_v3_derived_product_lifecycle.sql:165-206`). The new path must change only payload `DELETE`; Search receipts remain insert-only and `UPDATE`/`TRUNCATE` remain unconditional failures.

4. `v3_meta.guard_derived_product` takes advisory transaction lock `764003001`; rejects every delete; allows product change only when the base is `BUILDING`, `VALIDATING`, or `READY`; requires new products to start `BUILDING` without terminal evidence; preserves manifest identity; and permits only `BUILDING -> READY|FAILED` with the stated verified/failure evidence (`sql/v3/migrations/006_v3_derived_product_lifecycle.sql:32-95`). Its row trigger covers insert/update/delete and its truncate trigger calls the always-rejecting generic truncate guard (`sql/v3/migrations/006_v3_derived_product_lifecycle.sql:97-103`). Product metadata is therefore retained.

5. The registered archetype insert guard permits inserts only while the base is `BUILDING`, `VALIDATING`, or `READY` and the `system_archetype` product is exactly `BUILDING` (`sql/v3/migrations/011_v3_system_archetype.sql:77-99`). A shared rejector unconditionally blocks update/delete/truncate on archetype payload, summary, and chunk-receipt tables (`sql/v3/migrations/011_v3_system_archetype.sql:101-130`). Unlike Search, the purge migration opens **nothing** here: the archetype `DELETE` rejection stays as `011` installs it, the batch function's relation enum has no archetype member, and the purge requires the wide table to hold zero target rows, stopping on any (§§4.1, 4.3).

6. Cluster tables retain the generic generation guard; `cluster_run` has a lifecycle check but no separate lifecycle-transition trigger (`sql/v3/migrations/004_v3_search_spatial_clusters.sql:96-109`, `sql/v3/migrations/004_v3_search_spatial_clusters.sql:153-169`). **This purge deletes no cluster row.** `cluster_run` holds the run's algorithm/version, parameters, lifecycle and validation receipt, and its schema permits `PUBLISHED`; generation-level `derived_publication_audit` does not record cluster-run publication, so deleting a target generation's `cluster_run` could erase published provenance that no check here would see. The plan receipt must instead prove zero target rows in all three cluster relations, the action rechecks that before every phase, and any target cluster row stops the purge. Removing such rows would need its own reviewed design with an explicit cluster-run publication check.

7. The independent spatial guard rejects deletion of a spatial generation, enforces immutable identity and enumerated lifecycle transitions, and requires verification/failure/publication evidence (`sql/v3/migrations/012_v3_spatial_pyramid_decouple.sql:65-121`). Spatial `cell_summary` allows insertion only for `BUILDING|VALIDATING|READY` spatial generations and rejects update/delete/truncate (`sql/v3/migrations/012_v3_spatial_pyramid_decouple.sql:123-166`). No part of this guard is to change.

8. No special mutation triggers are installed on `current_derived_generation`, `derived_publication_audit`, or the registered scheduler tables; ordinary keys/checks apply (`sql/v3/migrations/003_ratings_v4_derived.sql:35-40`, `sql/v3/migrations/003_ratings_v4_derived.sql:72-80`, `sql/v3/migrations/013_v3_system_search_parallel.sql:4-26`). Absence of a trigger is not authorization: the purge contract makes all pointer, audit, scheduler, manifest, product, and chunk-receipt rows out of scope.

The bulk-write contract expressly notes that replica mode suppresses ordinary application and FK triggers and forbids using it for primary/foreign-key identity changes (`docs/development/bulk-database-write-safety.md:9-22`). This purge must not set `session_replication_role`, disable triggers, drop constraints, or use cascade.

## 2. INVARIANTS

1. **Never target current or ever-published derived data.** `parallel_v1`, every row it owns, and its current pointer remain unchanged. A partial build may never become current, application reads must resolve an explicit published generation, and published generations are immutable (`docs/development/v3-search-spatial-derived-data-decision.md:16-25`, `docs/development/v3-search-spatial-derived-data-decision.md:27-58`, `docs/development/v3-search-spatial-derived-data-decision.md:392-404`). Authorization also rejects any target mentioned as `from_generation_id` or `to_generation_id` in `derived_publication_audit`, even if it is not current.

2. **Retain the only current rollback/read foundation.** The architecture requires at least the previous compatible derived generation to be retained (`docs/development/v3-search-spatial-derived-data-decision.md:330-348`). This design does not claim either never-published candidate satisfies that rule; it preserves the sole PUBLISHED generation in the evidence and asks the owner to confirm the interpretation in section 7.

3. **Never touch canonical truth or the published spatial pyramid.** Canonical schemas remain source truth and Search/ratings/archetypes are reproducible derived outputs (`docs/development/v3-search-spatial-derived-data-decision.md:16-25`). The canonical pointer is `phase4c_full_20260827_r5`, publication sequence 4, and the spatial pointer is published `pyramid_v1`, sequence 1 (`docs/operations/evidence/2026-10-10-v3-derived-lifecycle-status-receipt.json:3-31`, `docs/operations/evidence/2026-10-10-v3-derived-lifecycle-status-receipt.json:858-881`). Both identities and their row counts are pre/post assertions, never mutation targets.

4. **Retain evidence.** Do not delete or rewrite `derived_generation`, `derived_product`, any publication audit, schema-migration ledger, build/search/archetype chunk receipt, scheduler plan/range, or the committed operation receipts. Generation manifests and product manifests are schema-declared retained (`sql/v3/migrations/003_ratings_v4_derived.sql:41-71`, `sql/v3/migrations/006_v3_derived_product_lifecycle.sql:32-103`). Add an append-only purge request/event ledger; never make missing payload indistinguishable from an unfinished or corrupt build.

5. **Fail closed at every mutation boundary.** Exact generation UUID/key/manifest hash, expected lifecycle, canonical/current-derived/current-spatial pointers and sequences, migration ledger hash, stopped workers, relation allowlist, target row count, published survivor row count, filesystem free bytes, WAL conditions, and absence of competing work must all match immediately before each phase. Full-Galaxy operations must be bounded/resumable with explicit lock policy and truthful progress (`docs/development/v3-search-spatial-derived-data-decision.md:350-364`).

6. **No bypass.** FK and application triggers stay enabled; no replica mode, trigger disable, cascade, arbitrary SQL/table input, or `TRUNCATE` is allowed. Replica mode would suppress the exact protections this operation needs (`docs/development/bulk-database-write-safety.md:9-22`).

7. **One small commit at a time.** A delete batch is one transaction with a bounded row limit and timeouts. A relation rewrite is a separate, explicitly approved phase. A failure never causes the operator to infer completion from logs; database row counts/catalog state are truth, following the existing resumable operator principle (`scripts/operator/actions/v3-system-search-validate-constraints.sh:1-6`).

8. **Do not promise recovery.** Safety comes from proving that only reproducible, never-published candidates are selected; permanently blocking their publication before deletion; preserving manifests/receipts; using transactional batches; preserving current data by predicate; and stopping between relations. The missing restore/PITR path remains visible and unauthorized (`docs/operations/infrastructure-status.md:73-79`).

## 3. AT LEAST THREE MATERIALLY DIFFERENT APPROACHES

PostgreSQL lock/WAL figures below are a design model to be verified on disposable PostgreSQL 18 and then remeasured by the read-only production plan. Repository evidence already establishes that plain deletion plus ordinary `VACUUM` makes pages reusable only inside the same table, while returning space to `/dev/md1` requires a table rewrite (`VACUUM FULL`, `CLUSTER`, or `pg_repack`) or partition drop (`docs/operations/v3-finder-capacity-decision-2026-10-10.md:143-166`). It also requires budgeting 10–15% of data written for WAL/temp/vacuum (`docs/operations/v3-finder-capacity-decision-2026-10-10.md:37-51`). Actual WAL retention, replication, and archive behavior are unverified and remain hard gates.

### 3.1 Approach A — bounded `DELETE` plus ordinary `VACUUM`

**Mechanism.** Execute child-first `DELETE ... WHERE derived_generation_id IN (...)` in bounded key/`ctid` batches through a guarded server function, then `VACUUM (ANALYZE)` each table. A plain `DELETE` does **not** return the measured space to the filesystem; ordinary `VACUUM` primarily makes dead pages reusable by future rows in the same relation (`docs/operations/v3-finder-capacity-decision-2026-10-10.md:151-156`). It therefore does not create filesystem headroom for new Search/archetype relations.

**Locks.** Design assumption to verify: each delete batch holds `ROW EXCLUSIVE` on its table and row locks only until that small transaction commits; ordinary `VACUUM` holds `SHARE UPDATE EXCLUSIVE` for its run but permits ordinary reads/writes. The batch limit and statement/lock timeouts bound each delete transaction; vacuum duration is not known.

**Peak additional disk and WAL.** Persistent rewrite space is approximately zero, but WAL is generated for every deleted heap tuple and index entry. The amount and retention are unmeasured. Filesystem free space stays near the starting 292.296 GB after WAL recycling rather than rising by the modeled 401.169 GB; the removed pages only become table-local free space. A 15% planning allowance on 401.169 GB is 60.175 GB, but this is a budget assumption derived from the repository's 10–15% guidance, not a measured WAL bound (`docs/operations/v3-finder-capacity-decision-2026-10-10.md:47-49`).

**Failure/host death.** A failed current batch rolls back; earlier batches remain committed and are counted on resume. A host death before vacuum leaves dead tuples and no filesystem reclamation. The current published generation remains logically intact because the delete predicate and guard exclude it. This approach does not meet the owner's filesystem-reclamation objective, so it is rejected as the final path.

### 3.2 Approach B — bounded `DELETE`, then one-relation-at-a-time `VACUUM (FULL, ANALYZE)`

**Mechanism.** Use the same guarded, child-first bounded deletes, but after both target generations reach zero rows for one payload relation, run `VACUUM (FULL, ANALYZE)` on that relation. Plain deletion still returns no filesystem space; `VACUUM FULL` performs the physical rewrite that returns old relation files to the filesystem (`docs/operations/v3-finder-capacity-decision-2026-10-10.md:151-159`). Process `system_search` first because it has no published survivor in the dated evidence, then opportunity, mechanics, and vector; this makes later survivor copies fit sequentially.

**Locks.** Design assumption to verify: batched deletes take the bounded locks described in approach A. `VACUUM FULL` takes `ACCESS EXCLUSIVE` for the entire table rewrite, blocking reads and writes of that relation until completion. The repository already treats an `ACCESS EXCLUSIVE` whole-table scan of roughly 198.5 million rows as minutes-long and unsuitable for an ordinary bounded migration (`sql/v3/migrations/010_v3_system_search_body_type_counts.sql:5-11`, `docs/operations/v3-finder-production-rollout-state.md:70-97`). Rewrite duration must be measured; it cannot be hidden inside the migration runner.

**Peak additional disk.** The table below is planning arithmetic, not authorization. It assumes proportional attribution equals compacted survivor/reclaim bytes, temp/WAL from a completed phase is recycled before the next phase, and a 15% working allowance is adequate. Every assumption must be replaced by live preflight measurements and rehearsal evidence.

| Rewrite phase | Modeled free before | New survivor copy | 15% WAL/temp allowance on delete + survivor write | Modeled peak additional | Modeled free after successful rewrite |
|---|---:|---:|---:|---:|---:|
| `system_search` (published survivor 0) | 292.296 GB | approximately 0 | 12.078 GB | about 12.078 GB | 372.819 GB |
| `economy_opportunity` | 372.819 GB | 131.079 GB | 39.813 GB | about 170.892 GB | 507.158 GB |
| `body_mechanics` | 507.158 GB | 103.823 GB | 31.534 GB | about 135.357 GB | 613.564 GB |
| `system_rating_vector` | 613.564 GB | 77.962 GB | 23.679 GB | about 101.641 GB | 693.465 GB |

The starting/reclaim/survivor inputs are sourced in section 1.6. Section C of the 2026-10-10 capacity decision correctly says that a rewrite “holds a full copy of the table in temporary space — impossible for a 265 GB table with 292 GB free” (`docs/operations/v3-finder-capacity-decision-2026-10-10.md:143-166`). That conclusion applies if the 265.418-GB `economy_opportunity` relation is rewritten first, before target rows are deleted and before any other relation returns space.

This design changes the peak sequence; it does not dispute section C. First, delete the two exact target generations so a rewrite copies only published survivors, not the full pre-delete relation. Second, rewrite `system_search`, whose dated evidence has no published survivor: its modeled 80.523-GB reclaim changes free space from 292.296 GB to 372.819 GB after a 12.078-GB allowance. Only then rewrite `economy_opportunity`: the modeled copy is 131.079 GB of published survivors rather than the original 265.418-GB relation, and its modeled 170.892-GB peak fits within 372.819 GB before that phase. The subsequent mechanics and vector phases copy modeled survivors of 103.823 GB and 77.962 GB after earlier reclamation has raised modeled free space again.

Every byte, GB, survivor size, allowance, peak, and post-phase free-space figure here is a **dated 2026-10-10 planning model**, based on proportional attribution rather than physical partitions. It is not an execution measurement or authorization. Fresh live measurement must replace every figure immediately before **each** delete and rewrite phase. Execution stops unless measured `free_bytes - survivor_copy_budget - measured_WAL/temp_budget` exceeds the owner-approved reserve.

**WAL.** Deletes generate WAL for removed rows/index entries; the full rewrite and rebuilt indexes generate additional WAL. Exact bytes and retained peak are unknown. The design's future plan action records start/end LSN, `pg_wal` bytes, archive/slot state, checkpoints, and free bytes, and will not begin the next phase until WAL has stabilized and the reserve gate passes.

**Failure/host death.** Each delete batch is atomic and resumable. Design assumption to prove in PostgreSQL 18 crash tests: if a full rewrite fails before its transactional filenode swap commits, the old relation remains authoritative; if it commits, the compacted relation is authoritative. A crash after logical deletion but before compaction leaves a valid bloated table and can be resumed. No step needs a backup restore to choose the correct database state; if PostgreSQL itself cannot recover locally, production work stops because no repository-authorized DR route exists (`docs/operations/infrastructure-status.md:73-79`).

### 3.3 Approach C — shadow partitioned tables, checked copy, atomic cutover, then partition drop

**Mechanism.** Create new generation-partitioned replacements for all payload tables, copy only retained rows, rebuild constraints/indexes/triggers, validate counts/seals, acquire short cutover locks, switch application/FK/view dependencies, and drop target-generation partitions. Future purges become `DROP TABLE`/detach-and-drop of exact generation partitions and return space immediately without row-by-row deletes. The repository identifies partition-per-generation as the most plausible long-term purge design (`docs/operations/v3-finder-capacity-decision-2026-10-10.md:156-166`).

**Locks.** The long copy/index phase can be read-compatible, but the final dependency/FK/view/table swap requires `ACCESS EXCLUSIVE` on multiple related tables. Because PostgreSQL dependencies follow object OIDs, a simple rename is not a valid cutover; the reviewed implementation would have to recreate every FK/view/trigger against the replacement. This is a design inference from the explicit dependency graph in section 1.3, not a repository-proven ready procedure.

**Peak additional disk and WAL.** Copying all published survivors needs at least 312.864 GB for the three ratings relations, before temp, indexes beyond the proportional model, and WAL. That already exceeds the dated 292.296 GB free, so the complete shadow set cannot be built on the measured volume without stepwise reclamation or new capacity. Copying relation by relation has similar peak arithmetic to approach B but adds multi-table cutover complexity. Every copied row/index is WAL-generating unless an additional durability design is introduced; no such authorized design exists in the repository.

**Failure/host death.** Before cutover, old tables remain authoritative and shadow objects can be discarded later. A cutover failure must roll back as one transaction; a host death uses PostgreSQL crash recovery to select the committed object graph. A defect in recreated dependencies could affect published reads, and there is no restore runbook. This approach is rejected for the immediate purge but recommended as a separate future schema design before another multi-generation build.

### 3.4 Approach D — guarded delete plus online `pg_repack`

**Mechanism.** Delete target rows through the governed function, then use `pg_repack` to copy live rows and indexes while maintaining a change log, with only a short final swap lock. This could reduce the long `ACCESS EXCLUSIVE` interval compared with approach B.

**Locks, disk, WAL, and failure.** It still needs approximately a live copy plus change-log/temp/WAL space and a final exclusive swap; it generates WAL for deletion, copied data/indexes, and concurrent-change capture. Failure before swap should leave the original relation, but that must be proved against the exact PostgreSQL 18/extension build. The current repository evidence does not establish that `pg_repack` exists in the PostgreSQL 18 production container; older PostgreSQL incidents are historical rather than current authority (`CLAUDE.md:19`, `docs/operations/infrastructure-status.md:36-40`). This approach is unavailable unless a new read-only inventory and separately reviewed extension authority prove it. It is not the recommendation.

Its minimum relation-copy peaks use the same dated survivor model as approach B: approximately 0 GB for empty Search, 131.079 GB for opportunity, 103.823 GB for mechanics, and 77.962 GB for vectors, each plus an unmeasured change log, temp files, and WAL. Against 292.296 GB starting free, a single relation might fit arithmetically, but the unverified extension, extra change-log growth, and unknown WAL retention prevent an execution claim. The long copy would use ordinary read/write-compatible locks plus extension triggers, followed by an `ACCESS EXCLUSIVE` final swap whose wait and hold time must be measured; failure or host death requires extension-specific cleanup proof before any retry.

## 4. YOUR RECOMMENDED APPROACH

Recommend **Approach B: explicit server-authorized bounded deletion followed by separately approved `VACUUM FULL` phases, with Search reclaimed first**. It is implementable with built-in PostgreSQL, preserves all audit/receipt records, and fits the dated arithmetic one relation at a time. It accepts a measured maintenance outage rather than assuming unverified extension availability or attempting a high-risk multi-table replacement.

### 4.1 Migration and fail-closed SQL design

**Numbering assumption:** the current SHA has no migration `015`, while the ROADMAP reserves `015` for product publication (`docs/ROADMAP.md:181-205`). Name the purge migration `016_v3_governed_derived_purge.sql` only if the implementation branch has `015` in that role; otherwise select the next ledger name without renumbering or rewriting an applied migration. Register it after rewritten `011`, `013`, and `015` because the production runner applies the complete pending prefix (`docs/ROADMAP.md:193-216`).

The migration owns `BEGIN`/`COMMIT`, uses bounded lock/statement timeouts for its metadata-only DDL, and creates:

1. `v3_meta.derived_generation_purge_request`: immutable `purge_id`, exact target UUID/key, target manifest SHA-256, original state, expected canonical/current-derived/current-spatial IDs and publication sequences, reviewed plan SHA-256, source Git SHA, actor/reason, created time, and a check that the target key is one of the two owner-approved keys. A guard rejects update/delete/truncate. No caller-supplied relation or generation name is interpolated.

2. `v3_meta.derived_generation_purge_event`: append-only event sequence keyed by `purge_id`, event kind — a closed enum of the phase events `AUTHORIZED`, `BATCH_COMMITTED`, `RELATION_LOGICALLY_EMPTY`, `REWRITE_STARTED`, `REWRITE_VERIFIED`, `COMPLETED`, `FAILED_STOP` **and the operational events the recovery rules of section 4.2 append: `BATCH_STARTED` (appended in its own committed transaction **before** the batch's delete runs, carrying the batch backend's PID and `backend_start` and the batch's deterministic key range, and closed by the `BATCH_COMMITTED` that the delete transaction appends or by `BATCH_ROLLED_BACK` from the wrapper after a cancel or failure — the open `BATCH_STARTED` is what `v3_meta.cancel_purge_batch` authenticates against, exactly as `REWRITE_STARTED` serves the rewrite cancel), `BATCH_ROLLED_BACK`, `SERVICES_QUIESCED`, `SERVICES_RESTORED`, `AUTOVACUUM_DISABLED`, `AUTOVACUUM_RESTORED`, `WRITER_FENCE_ENABLED`, `WRITER_FENCE_RESTORED`, `REWRITE_CANCEL_REQUESTED`, `BATCH_CANCEL_REQUESTED`** (every kind the design says is written to the ledger is in the enum, and a contract test asserts the two lists agree), and an `operational_payload jsonb` column that `AUTOVACUUM_DISABLED` fills with the relation's **prior** `reloptions` state — `autovacuum_enabled` explicitly `true`, explicitly `false`, or unset — so that after an interrupted dispatch the restore reads the recorded prior value from the ledger, never from the current catalog, which can no longer distinguish an originally unset relation from one already disabled; `AUTOVACUUM_RESTORED` records the value it wrote, `SERVICES_QUIESCED` the exact container set, `WRITER_FENCE_ENABLED` the application role's **prior** `default_transaction_read_only` role setting (set `on`, set `off`, or unset, read from `pg_db_role_setting`) and `WRITER_FENCE_RESTORED` the value written and the number of sessions recycled, and the two `*_CANCEL_REQUESTED` kinds the condition that tripped. Tests: a dispatch killed after disabling autovacuum on a relation whose option was unset is restored to unset, and one whose option was explicitly `false` is left `false`, hard-coded relation code, relation OID, `relfilenode_before`/`relfilenode_after` (rewrite events; `before` recorded by `REWRITE_STARTED`, `after` by `REWRITE_VERIFIED`), the rewrite backend's PID and `backend_start` (recorded by `REWRITE_STARTED`, so a reused PID is never mistaken for it) and a `recovered` flag, rows affected/remaining, target and published survivor counts, relation bytes, filesystem bytes, WAL LSN/bytes, receipt SHA, timestamp, and failure evidence. A guard rejects update/delete/truncate. The latest event is progress truth; history is never overwritten.

3. `v3_meta.begin_derived_generation_purge(...)`: takes advisory transaction lock `764003001` **and the spatial publication lock `764004001`** that `v3_spatial.publish_spatial_pyramid` takes (so a spatial publication cannot commit between this check and this commit — the derived lock alone does not exclude it), locks current canonical/current derived and both target generation rows and the `current_spatial_generation` singleton `FOR SHARE`, and rejects unless all expected identities/sequences/hashes/states match, workers were separately attested stopped by the plan receipt, targets are not current, neither target appears in `derived_publication_audit`, and the exact reviewed plan hash is unused. In the same transaction it inserts immutable requests/events and transitions `p4: BUILDING -> FAILED` and `opt1: VALIDATING -> FAILED` with explicit failure evidence stating that owner-authorized purge superseded the build. Both transitions already exist in the manifest guard (`sql/v3/migrations/003_ratings_v4_derived.sql:53-59`). A committed `FAILED` state makes the targets unpublishable because publication accepts only verified `READY`/`RETIRED` candidates (`sql/v3/migrations/006_v3_derived_product_lifecycle.sql:245-267`).

4. `v3_meta.purge_derived_payload_batch(purge_id, relation_code, max_rows)`: `SECURITY DEFINER` owned by the table owner, fixed `search_path`, revoked from `PUBLIC`, and executable only by a dedicated `NOLOGIN` role, `v3_derived_purge_executor`, that holds `EXECUTE` on the purge functions, the read access `status`/plan need, and `MAINTAIN` on exactly the four rewrite tables (`system_search`, `economy_opportunity`, `body_mechanics`, `system_rating_vector`) — the PostgreSQL 17+ privilege `VACUUM (FULL)` requires of a non-owner, which permits maintenance commands but no row change — and **no** `INSERT`/`UPDATE`/`DELETE`/`TRUNCATE` on any payload or ledger relation and no ownership. **The governed connection is the table owner** (`edfinder_v3`, the role the migration runner and deploy tooling use), and against its owner — possibly a superuser in this deployment — no in-database guard is a boundary: an owner can issue a direct `DELETE` or disable a trigger. So the action's first statement in every session is `SET ROLE v3_derived_purge_executor`; its SQL is fixed text in the repository, and a contract test asserts that it begins with that statement and contains no `RESET ROLE`, `SET SESSION AUTHORIZATION`, `ALTER TABLE` or DML outside the functions. That bounds what the purge action itself can do: it can only call the functions, which enforce the batch limit and append the event in the same transaction. It does not, and cannot, bound a deliberate operator using the owner role outside the action; that remains governed by the protected workflow, environment approval and review, which is stated rather than implied. Creating the role needs `CREATEROLE` or superuser on the migration role: the implementation PR verifies that read-only before relying on it and stops to ask if it is absent. **Creating the role is not enough for `SET ROLE`:** on PostgreSQL 18 `createrole_self_grant` is empty by default, so a non-superuser `edfinder_v3` that creates `v3_derived_purge_executor` does not thereby become a member of it, and the action's mandatory first statement would fail. `016` therefore also executes `GRANT v3_derived_purge_executor TO edfinder_v3 WITH SET TRUE, INHERIT FALSE` (membership with the `SET` option only, so the login role gains no inherited privileges from the executor), and the disposable tests run the whole purge path as a **non-superuser** `edfinder_v3` with `CREATEROLE` — the supported configuration — as well as under a superuser, asserting that `SET ROLE` succeeds in the first and that the executor's `MAINTAIN`-only privileges hold in both. It accepts `max_rows` only in `1..100000`; maps a closed enum to static SQL; rechecks the request, target `FAILED` state, current pointers (holding the same two advisory locks and the spatial singleton `FOR SHARE` as `authorize`, as does every completion function), nonpublication, dependency phase, and advisory lock; deletes one deterministic indexed batch for exactly one target; and appends a batch event in the same transaction. Mixed-generation statements fail atomically. A custom transaction-local setting may carry `purge_id` to triggers, but the setting alone is never authority: the trigger must join the immutable request, verify the target UUID/state/current pointer/plan, and verify the executing function context.

5. `v3_meta.complete_derived_payload_relation(...)` and `v3_meta.complete_derived_generation_purge(...)`: append completion events only after exact target counts are zero for all applicable payload relations, published counts match the frozen preflight counts, metadata/receipts still exist, pointers are unchanged, FK checks pass, and post-rewrite relation/free-space measurements exist. Re-execution is an idempotent no-op only after database evidence proves the exact phase complete.

Guard changes are deliberately narrow:

- Replace only the `DELETE` branch of `v3_derived.guard_generation_write`: normal deletion is no longer permitted merely because a generation is `BUILDING`; deletion is permitted only for transition rows belonging to an active exact purge request whose target is `FAILED`, noncurrent, and never published. `INSERT` and both `UPDATE` transition-table checks retain their existing lifecycle behavior; `TRUNCATE` remains unconditional deny (`sql/v3/migrations/003_ratings_v4_derived.sql:189-216`).
- Replace Search's unconditional payload-delete trigger with an `AFTER DELETE ... REFERENCING OLD TABLE AS changed_rows` authorization guard, so unauthorized work rolls back. Keep Search `UPDATE` and `TRUNCATE` unconditional deny and keep all three `search_build_chunk` mutation rejects unchanged (`sql/v3/migrations/006_v3_derived_product_lifecycle.sql:165-206`).
- Leave the wide `system_archetype` table's guards exactly as the rewritten `011` installs them (payload inserts only while BUILDING; `UPDATE`/`DELETE`/`TRUNCATE` rejected; every `archetype_build_chunk` mutation rejected, `sql/v3/migrations/011_v3_system_archetype.sql:101-130`): the purge authorizes no archetype delete, the batch function's relation enum has no archetype member, and `system_archetype_summary` is a view with no payload of its own.
- Cluster relations continue through the tightened generic guard, and the batch function's relation enum has no cluster member, so no purge request can authorize a cluster delete. Spatial guards, generation/product manifest guards, publication functions, current pointers, audits, chunk receipts, and scheduler tables are unchanged.

The migration must not perform the purge or `VACUUM FULL`; it only installs the fail-closed capability. Adding it requires its exact hash/path in `sql/v3/migration-manifest.txt`, a recut `deploy/v3-production/target-authority.json` schema transition and every compatible intermediate prefix, and regenerated schema identity. The current manifest documents ledger-name/path/hash semantics (`sql/v3/migration-manifest.txt:1-13`), while the governed migration runbook requires manifest registration, transition/compatibility attestation, identity regeneration, exact-head acceptance, plan review, and separate apply (`docs/operations/v3-production-schema-migration.md:72-85`).

### 4.2 Operator actions, workflow, and receipts

Use two surfaces:

1. Keep `v3-derived-purge-plan` and `v3-derived-purge-status` as read-only choices in `.github/workflows/chatgpt-ed-new-ops.yml`.
2. Add a dedicated `.github/workflows/v3-production-derived-purge.yml` for mutation, modeled on the protected production schema-migration workflow, with `workflow_dispatch` only, environment `v3-production`, literal target confirmation `ed-finder-prod/nb79a3d.mevnode.com`, exact current-`main` re-fetch after approval, pinned known-host SSH, workflow-level concurrency group `v3-production-application-authority` (shared with deployment and schema migration) **and** job-level group `chatgpt-ed-new-ops` (shared with every worker launched through the ops workflow and with `v3-spatial-pyramid.yml`), so no governed production mutator can be dispatched while a purge phase runs, `contents: read` plus only the narrow permission needed to authenticate/download the successful plan artifact, and no request-controlled target/relation/path. The stronger migration workflow already demonstrates protected manual inputs, exact-main gates, pinned host trust, reviewed plan authentication, and 180-day receipts (`.github/workflows/v3-production-schema-migration.yml:24-38`, `.github/workflows/v3-production-schema-migration.yml:45-105`, `.github/workflows/v3-production-schema-migration.yml:106-202`).

Implement `scripts/operator/actions/v3-derived-generation-purge.sh` with fixed modes. The workflow exposes each destructive phase as a literal choice, not a free string:

- `authorize` (marks both exact targets `FAILED`; no payload deletion);
- `verify-system-archetype-empty` (the wide table must hold zero target rows and the summary view none; the mode deletes nothing and stops the purge on any row);
- `delete-system-search`;
- `rewrite-system-search`;
- `delete-economy-opportunity`;
- `rewrite-economy-opportunity`;
- `delete-body-mechanics`;
- `rewrite-body-mechanics`;
- `delete-system-rating-vector`;
- `rewrite-system-rating-vector`;
- `restore-services` (restarts exactly the recorded quiesced set after an interruption);
- `complete`;
- `status`.

Each delete dispatch may run a bounded loop of small DB transactions for only that relation, stopping when its wall-clock budget expires and resuming from database counts on the next dispatch. **The loop does not outlive its workflow job's fences.** GitHub concurrency groups fence only while the job runs, so a launcher that returned while the loop continued (the pattern of the detached validation launcher, `scripts/operator/actions/v3-system-search-validate-constraints.sh:258-273`) would let a deployment, another operator action or `restore-services` start mid-batch. The protected workflow job therefore **stays running and polls the loop until it has terminated** — normal exit, budget expiry or `FAILED_STOP` — with the job's `timeout-minutes` set above the loop's wall-clock budget plus the longest batch, and the loop's budget is the only thing that ends it early. Independently of GitHub, the loop holds a **host-side lease**, a non-blocking `flock` on `/run/lock/edfinder-v3-derived-purge.lock` for its whole life (the same mechanism as the pgBackRest schedule lock), and every governed production mutator — the application deployer, the schema-migration apply, the spatial publisher, the ops-workflow worker launchers and `restore-services` — refuses to start while that lock is held. **The lease is ephemeral and the ledger is not**, so the same mutators also read the purge ledger before they start and refuse while it shows any unresolved purge state. The rule is per kind, because the fence states are deliberately left open between the dispatches of one relation: an open `BATCH_STARTED` or `REWRITE_STARTED` blocks **every** mutator, purge dispatches included, until `status` resolves it from database evidence; a `SERVICES_QUIESCED` without `SERVICES_RESTORED`, or a `WRITER_FENCE_ENABLED` without a verified `WRITER_FENCE_RESTORED`, blocks everything except the purge's own `restore-services`; and an `AUTOVACUUM_DISABLED` for relation R without its `AUTOVACUUM_RESTORED` blocks every non-purge mutator and every purge phase for a **different** relation, while a further `delete-R` dispatch (a loop that ended on its wall-clock budget) or the `rewrite-R` dispatch **adopts** the open fence — it is the state those continuations expect, and restoring it between them would admit exactly the unbudgeted autovacuum work the fence exists to prevent — and the rewrite's verification is what restores it. A host reboot or a dead purge process frees the lock, but it cannot clear the ledger, and only the purge's own resolution paths can. That check is one shared read-only query in `scripts/operator/lib/` that each mutator calls first, with a contract test per mutator that it refuses on each unresolved kind. So a job cancelled or an SSH session lost mid-batch cannot be overtaken: the loop finishes its current batch, sees its lost controller on the next between-batch check (the workflow run id it was given is no longer running, checked through the receipt it writes) and stops with `FAILED_STOP`, and until then the lease keeps everything else out. Tests: the launcher does not return while the loop runs; a loop whose controller disappears stops after at most one more batch; a deploy attempted while the lease is held is refused. Each rewrite is its own owner-reviewed dispatch. The script pins the exact target host/FQDN, PostgreSQL container/database/user, both target UUID/key pairs, published/canonical/spatial pointers, guard migration name/hash, source SHA, relation enum, and expected migration-set identity. Existing mutating actions demonstrate exact CPython 3.14, host/container/default-context validation, fixed local `psql -X --no-psqlrc --no-password`, and exact migration hash verification (`scripts/operator/actions/v3-system-search-validate-constraints.sh:11-34`, `scripts/operator/actions/v3-system-search-validate-constraints.sh:119-148`, `scripts/operator/actions/v3-system-search-validate-constraints.sh:211-260`).

Immediately before every destructive phase, rerun worker/pointer/lifecycle/size checks equivalent to `v3-derived-lifecycle-status`; that action already treats unknown worker state as failure, records all pointers/generations/products, sizes relations/indexes, resolves the actual PostgreSQL mount, and derives readiness only from stopped workers plus complete inspection (`scripts/operator/actions/v3-derived-lifecycle-status.sh:267-301`, `scripts/operator/actions/v3-derived-lifecycle-status.sh:351-539`, `scripts/operator/actions/v3-derived-lifecycle-status.sh:541-622`, `scripts/operator/actions/v3-derived-lifecycle-status.sh:737-858`).

For a rewrite, the wrapper first takes the **same host lease** the delete loop holds (`/run/lock/edfinder-v3-derived-purge.lock`, non-blocking `flock`) and keeps it until the rewrite backend has stopped **and** verification or recovery has appended `REWRITE_VERIFIED` or `FAILED_STOP` — the database advisory lock is not shared by the deployer, the migration apply or the spatial publisher, so without the host lease a cancelled workflow or dropped SSH session would release both GitHub concurrency groups while `VACUUM FULL` kept running and a competing mutator could start; the workflow job likewise stays running and polls until the wrapper exits, exactly as for a delete dispatch. One `psql` session then acquires advisory session lock `764003001`, rechecks all identities/counts/free-space/WAL gates, then runs three steps that cannot share one transaction, because PostgreSQL refuses `VACUUM` inside a transaction block: (1) a committed transaction appends `REWRITE_STARTED` carrying the relation's current `pg_class.relfilenode` and sizes; (2) fixed `VACUUM (FULL, ANALYZE) v3_derived.<allowlisted_table>` runs on its own; (3) after rechecking — including that `pg_stat_user_tables.last_analyze` for the relation is later than the `REWRITE_STARTED` time, since the analysis runs in its own transaction after the rewrite commits — a committed transaction appends `REWRITE_VERIFIED` with the new `relfilenode` and sizes; then the lock is released. If step 1 fails, the rewrite never starts. If step 3 fails, or the wrapper dies after step 2, the relation may already have been replaced, so the design does not pretend otherwise: the ledger shows `REWRITE_STARTED` with no `REWRITE_VERIFIED`, and that state is resolved from database evidence rather than assumed. `status` reports it as unresolved; re-dispatching the same `rewrite-*` mode first checks that no `VACUUM FULL` of that relation is running (`pg_stat_progress_cluster`) and compares `relfilenode` with the value recorded in `REWRITE_STARTED` — changed means the rewrite committed, so the action does **not** rewrite again — but it does not yet know that the analysis finished either, because `VACUUM (FULL, ANALYZE)` commits the rewrite and then runs `ANALYZE` in a separate transaction, so an interruption between the two leaves a new `relfilenode` with stale statistics. It therefore runs `ANALYZE v3_derived.<allowlisted_table>` (permitted by the executor's `MAINTAIN`), verifies `pg_stat_user_tables.last_analyze` for that relation is later than the `REWRITE_STARTED` time, and only then appends `REWRITE_VERIFIED` marked `recovered: true` with that evidence; unchanged means the rewrite rolled back, and the phase may run normally. `VACUUM FULL` always assigns a new `relfilenode` and `TRUNCATE`, the only other way to change it, stays denied, so the comparison is unambiguous. `complete` refuses while any relation has an unresolved `REWRITE_STARTED`. No shell variable becomes an SQL identifier except through a closed internal `case` mapping. A short `lock_timeout` fails rather than waiting behind unknown work; the statement timeout is a separately reviewed per-table bound based on rehearsal, not zero.

**The 100 GB floor is enforced during a rewrite, not only before it.** The primary guard is the pre-start bound: a rewrite starts only if its rehearsal-based projected peak, multiplied by 1.5, still leaves at least 100 GB free. The backstop is a monitor in the same action that polls, at a short interval while `VACUUM FULL` runs, filesystem free space, `pg_wal` size **and the gate-2 WAL-health conditions — no replication slot inactive or retaining WAL, archiver not failing (`pg_stat_archiver.last_failed_time` not later than its `last_archived_time`), `pg_wal` on the data filesystem**; if free space falls below the floor **or either WAL-health condition fails**, it cancels **the backend PID it recorded when its own rewrite started**, and no other session, and records which condition tripped. The rewrite is the one long-running phase that cannot re-run the gate between steps as the delete loop does, so the monitor is where gate 2 lives for it. It cannot do that with `pg_cancel_backend` directly: the rewrite session is logged in as the owner role and only `SET ROLE`s to `v3_derived_purge_executor`, and PostgreSQL lets a caller signal a backend only if the caller is a member of that backend's **logged-in** role (a superuser's backend only from a superuser), so the deliberately unprivileged executor would be refused and the rewrite would keep consuming space. The migration therefore provides `v3_meta.cancel_purge_rewrite(purge_id, relation_code)` (and its batch counterpart `v3_meta.cancel_purge_batch(purge_id, relation_code)`, same contract against the PID and `backend_start` the open `BATCH_STARTED` event recorded before the batch's delete began — with no open `BATCH_STARTED` it refuses and signals nothing), `SECURITY DEFINER` owned by the owner role and executable only by the executor: it looks up the open `REWRITE_STARTED` event for that purge and relation, requires a live `pg_stat_activity` row with exactly the recorded PID **and** `backend_start`, running `VACUUM` on that relation (`pg_stat_progress_cluster.relid` equal to the recorded OID), and only then calls `pg_cancel_backend` on it, appending the attempt to the ledger; any mismatch refuses without signalling anything. Tests: under the executor role the function cancels the recorded rewrite; it refuses a different PID, a reused PID with a different `backend_start`, a relation without an open `REWRITE_STARTED`, and a backend not running that `VACUUM`; and direct `pg_cancel_backend` from the executor on that backend is shown to be refused, which is why the function exists. A cancelled `VACUUM FULL` rolls back: the old relation stays authoritative and the partial new files are removed. The disposable crash rehearsal must prove this for cancellation exactly as it does for a crash. The phase then stops with a `FAILED_STOP` event and the measured figures.

**The same floor is enforced between delete batches, not only before a delete dispatch.** A delete dispatch may run a long detached loop over up to about 134 GB of target rows, and its WAL volume is unknown until rehearsal, so a per-phase preflight alone cannot stop it. Before **every** batch the loop re-measures free bytes on the PostgreSQL data filesystem and re-runs the WAL-health gate (`pg_wal` on that filesystem; no replication slot retaining WAL; archiver not failing — gate 2). The loop starts the next batch only if free space is at least the 100 GB floor **plus 1.5 × that relation's rehearsal-measured peak filesystem growth per batch — WAL plus temporary and work files together, measured as the peak drop in free bytes on the data filesystem during a rehearsal batch, not WAL alone** — and the WAL gate passes, so the floor still holds after the batch it is about to start, not only before it. The statement-level guards materialize an `OLD TABLE` transition relation of up to 100,000 rows and the deterministic batch selection can spill to disk, so the temp growth is real and is part of the owner's floor; a batch-level monitor also polls free space while the batch runs and cancels the batch's own backend (through `v3_meta.cancel_purge_batch`, the same recorded-PID pattern as the rewrite cancel) if the floor is crossed mid-batch, which rolls that batch back. Otherwise it starts no further batch, appends a `FAILED_STOP` event with the measured figures and exits; the committed batches stand and the next dispatch resumes from database counts. Each batch is one bounded transaction (at most 100,000 rows under a statement timeout); the rehearsal measures its peak filesystem growth (WAL and temp) per relation, the receipt records the figure the loop reserved, and the rehearsal must show it is under 1 GB, or the batch bound is lowered until it is.

**Autovacuum is fenced on the active relation for its delete phase.** Large committed deletes make the relation eligible for autovacuum, whose table and index work and WAL are absent from the per-batch WAL reservation and which the action has no authority to cancel — and the rewrite that follows makes that work pointless. So at the start of a delete phase a `SECURITY DEFINER` function, `v3_meta.purge_set_relation_autovacuum(purge_id, relation_code, enabled)`, executable only by the executor and limited to the four allowlisted relations, sets `autovacuum_enabled = false` on the active relation and appends the change to the ledger; the rewrite's verification restores it to the recorded prior value, and `complete` refuses while any of the four is not restored. The phase refuses to start while an autovacuum is already running on that relation (`pg_stat_progress_vacuum`), and it re-checks before every batch, stopping with `FAILED_STOP` if one appears. Anti-wraparound autovacuum ignores the setting, so the plan receipt also requires each relation's `age(relfrozenxid)` to be comfortably below `autovacuum_freeze_max_age` (the margin set from rehearsal batch counts), or the phase does not start. A dispatch that dies leaves the setting disabled; `status` reports it and the next dispatch or `complete` restores it.

**Every production database writer is fenced off for the whole phase, not checked once.** A point-in-time check cannot hold: the production API keeps a write-capable connection pool (it also runs the EDDN simulation ingest), a pooled connection with no current transaction ID can start one a moment after the check, and a worker detached by an earlier dispatch keeps running after its workflow ends. So every destructive phase (each delete dispatch and each rewrite; `authorize` and `complete` are single transactions and need only the check) **quiesces the write-capable application services first** — every application container with database write access, enumerated from the deployment target authority rather than discovered, at minimum the API — and keeps them stopped until that phase's verification has completed, then starts the same containers again (no image change) and checks their health. While they are down, the action confirms from `pg_stat_activity` that no client session other than its own is connected to the operating database, re-runs the named-worker check from `v3-derived-lifecycle-status` before every batch and every rewrite, and stops if anything else appears. The workflow already holds the deployment concurrency group, so no deploy can restart them mid-phase. **The host's scheduled pgBackRest jobs are fenced too**: the daily differential, weekly full and weekly verify timers run outside both concurrency groups and outside the containers (`deploy/v3-production/backup/README.md`), and their wrapper serializes only on the host lock `/run/lock/edfinder-v3-pgbackrest-schedule.lock` (`deploy/v3-production/backup/pgbackrest-operation.sh:6-17`). For the whole phase the action holds that same lock with a non-blocking `flock`, refusing to start if it is already held, and also refuses if any `pgbackrest` backup or verify process is running in the PostgreSQL container — the wrapper's own check. A timer that fires meanwhile takes the wrapper's existing `SKIP` path; because the timers use `Persistent=false`, a skipped run is not caught up, so the receipt records each scheduled run the phase overlapped. WAL archiving is not fenced: it is governed by the gate-2 archiver checks. This is a **full-application** service outage: the API also serves the shipped map, journal, watchlist, pins and compare features, so the gate-3 answer (which covers the Finder/ratings product having no users) does not authorize it. It is authorized only by the owner's answer to **gate 3b** (§7), which either approves the outage and its unreplayed EDDN simulation ingest gap per phase or selects the read-only writer fence described there, under which the API stays up and only application writes fail closed for the phase. Until gate 3b is answered no destructive phase runs. The receipt records each service stopped and started, with times, under its service-change flag. **An interrupted phase must not leave the application down.** The deployment's `restart: unless-stopped` does not bring back a container that was explicitly stopped, so before stopping anything the action records the exact running set — container names and IDs — both in the purge ledger (a `SERVICES_QUIESCED` event) and in a root-owned host file, and installs a host-side exit/signal trap. **The trap restores nothing while the purge is still writing, and releases nothing until restoration is durable:** it first signals the batch loop to stop after its current batch and waits for the loop process to exit, or for a rewrite cancels the recorded backend through `v3_meta.cancel_purge_rewrite` and waits until `pg_stat_activity` shows it gone and `pg_stat_progress_cluster` shows no rewrite of that relation; then it restarts exactly the recorded container set, health-checks it and appends `SERVICES_RESTORED` (and, under option (b), runs the fence restore and its verification); and **only after `SERVICES_RESTORED` is committed does it release the host lease**, so no deploy, migration, spatial publication or `restore-services` dispatch can acquire the lease and race the cleanup. Restoring the writers while the loop was committing its final batch would reopen the writer fence mid-batch and invalidate that batch's count and WAL assumptions. Tests: a cancellation during a batch restarts the services only after the loop has exited; the lease is never released while the loop PID is alive. For the cases a trap cannot cover (the SSH session killed hard, the host rebooting), a `restore-services` mode, also on the protected workflow, restarts exactly the recorded set, health-checks it, and appends `SERVICES_RESTORED`; it is idempotent. Every destructive mode refuses to start while the ledger shows a `SERVICES_QUIESCED` without a matching `SERVICES_RESTORED`, and `status` reports that state first.

Every plan/start/status/rewrite result is JSON-only and includes:

- schema version, operation, phase, status/result/failures;
- workflow run ID, exact trusted source SHA, script SHA, guard-migration expected/live SHA, migration-set identity, and verified flags;
- host/FQDN/container/database/PostgreSQL version and data-mount identity;
- purge ID and reviewed plan SHA;
- target UUID/key/manifest hash/original and current lifecycle for both targets;
- canonical, current-derived, and current-spatial UUID/key/sequence before and after;
- every named worker and observed state;
- fixed relation, batch limit, rows affected this run/cumulative/remaining, exact published survivor rows before/after, and FK-check result;
- heap/index/total bytes and filesystem total/used/free bytes before/after;
- `pg_wal` bytes, current WAL LSN before/after, WAL-byte delta, archive status, replication slots/lag, checkpoint counters, temp bytes, and the configured reserve/abort threshold;
- lock/statement/wall-clock timeouts, backend/runner state, rewrite start/completion, and database transaction outcome;
- explicit booleans for database writes, canonical writes, pointer/publication changes, service changes, filesystem reclamation, migration execution, and application deployment. If interruption prevents proving a write outcome, use `null`, never a false success claim.

The workflow uses `tee`, uploads receipts with `if: always()` and `if-no-files-found: error`, retains them at least 180 days, and the owner-reviewed accepted receipts are committed under `docs/operations/evidence/` in a later evidence-only PR. Current mutating actions already retain start/status artifacts but only warn when absent and keep them 30 days (`.github/workflows/chatgpt-ed-new-ops.yml:175-210`, `.github/workflows/chatgpt-ed-new-ops.yml:337-399`); irreversible no-restore work needs the stronger contract.

Do not invoke purge until the live ledger proves the full target (`docs/operations/v3-production-schema-migration.md:56-64`). |
| Fresh purge plan | Worker/pointer/state/count/disk/WAL fact missing or changed | Read-only phase returns `stopped`; no authorization. The dated receipt is never substituted for live proof; its own worker result was not ready (`docs/operations/evidence/2026-10-10-v3-derived-lifecycle-status-receipt.json:782-803`). |
| Authorization | One target update/request/event fails | One DB transaction rolls back. No payload is deleted. If commit succeeds and the host dies immediately, both targets are durably `FAILED` with immutable requests; published data is unchanged. Resume through `status`, never by recreating a request. |
| Batched delete | Statement timeout, FK violation, trigger rejection, connection loss, or host death | The current batch rolls back or commits atomically; already committed batches remain legitimate. Count target rows and resume the same phase. The exact predicate cannot touch published UUIDs; post-batch published-count drift is a critical stop. No restore is required because only owner-rejected, reproducible payload is removed. |
| Receipt/artifact upload after a committed batch | GitHub runner/network failure | DB purge events and exact row counts are authoritative; workflow reports write outcome `null` if it cannot prove commit. Do not rerun blindly. `status` reconstructs state and emits a replacement receipt; owner review is required before the next phase. |
| Lock acquisition for rewrite | Readers/writers hold incompatible locks beyond timeout | `VACUUM FULL` does not start; no physical state changes. Report blockers without terminating them, and reschedule. Beyond quiescing the enumerated application services for the phase (§4.2), the purge action may cancel no backend except the one running its own rewrite. |
| Disk/WAL gate before rewrite | Free-minus-survivor-minus-WAL/temp-minus-reserve is nonpositive, archive/slot retention is unhealthy, or metrics are unavailable | Rewrite does not start. Logical deletion may already be complete, leaving dead tuples and table-local reusable pages; published reads remain logically valid. Owner must add capacity or authorize a separately reviewed alternative. Never lower the reserve automatically. |
| Host death/termination during `VACUUM FULL` | Rewrite interrupted before or after its transactional swap | Required rehearsal must prove PostgreSQL 18 exposes exactly the old or new relation after crash recovery, never a half-swapped relation. On restart, verify relation/index validity, published count/seal, target count, pointer, and free bytes before recording/retrying. This depends on local transactional crash recovery, not backup restore. |
| Rewrite commits but verification fails | Published count, FK, index, pointer, or size differs | Stop all later phases. Do not delete another relation and do not claim completion. Because no restore path is authorized, this is an owner/escalation boundary; only read-only diagnosis is allowed until a new reviewed repair authority exists (`docs/operations/infrastructure-status.md:73-79`). |
| Failure between child and parent phases | Child target rows are gone; parent target rows remain | This is a valid, noncurrent partial purge. Immutable events identify the boundary. Resume only at the same or next dependency-safe phase after fresh preflight; never recreate deleted child rows merely to roll back. |
| Failure after all deletes but before completion | Payload is absent but final audit checks/receipt incomplete | Targets remain `FAILED` and cannot publish. Run read-only status and the idempotent completion verifier. Do not infer completion from zero rows alone; retained evidence, pointers, survivor counts, FK/index validity, and space/WAL must all pass. |
| PostgreSQL will not start or the host/storage is lost | Local crash recovery cannot restore service | Stop. The repository has no authorized PostgreSQL 18 restore/PITR/DR command (`docs/operations/infrastructure-status.md:73-79`). This design deliberately does not invent one; external owner infrastructure action or a separately reviewed recovery runbook is required. |

The irreducible risk is a PostgreSQL/storage defect during a rewrite of a shared table that also contains the published generation. Predicate guards prevent logical deletion of published rows, and transactional rewrite semantics are to be crash-tested, but the absence of a restore path means an engine/filesystem failure cannot be remediated by this repository. That risk must be explicitly accepted at each rewrite dispatch.

Enabling is two steps because a catalog change is invisible to other sessions until it commits and role defaults are read only at login: **first**, in one transaction that then **commits**, the function reads the application role's current `default_transaction_read_only` setting from `pg_db_role_setting`, appends `WRITER_FENCE_ENABLED` with that prior value and runs `ALTER ROLE <application role> SET default_transaction_read_only = on`; **second**, after the commit, the action terminates that role's other sessions (`pg_terminate_backend`; the owner-role function may signal its own role's backends) so the pools reconnect read-only, and verifies with a fresh probe connection of that role that a new session reports the setting `on`. The phase proceeds only after the second step's verification; a probe taken before the commit would prove nothing about post-commit sessions. The purge session itself runs `SET default_transaction_read_only = off` after `SET ROLE`, which a session may always do. The API stays running: reads (map, Finder 503, journal browsing) keep working and every application write (watchlist, pins, journal import, EDDN ingest) fails closed with a logged error for the phase.
