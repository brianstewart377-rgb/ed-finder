## Catalogue density comparison

### V2 baseline and evidence quality

V2 fetched heatmap cells through `frontend/src/hooks/useDensity.ts` and adapted
them in `frontend/src/features/map-foundation/production-parity.ts`. The adapter
discarded cell count `n` for presentation and used ratings `avg_score` in the
visual contract. `frontend/src/features/map-foundation/SceneContents.tsx`
hard-disabled `DensitySwirl` while always mounting `VolumetricGalaxy`, whose
visible Galaxy form was generated by spiral-arm, disk and bulge equations.

V2 tests established fetch/prop composition and independently evaluated opacity
expressions. They did not inspect mounted factual density geometry in the
production renderer, so they could not detect that the fetched heatmap was not
visible. The V2 strengths worth preserving are bounded aggregate input, typed
buffers and an immediately legible whole-Galaxy context. Its release-blocking
defect is that procedural form could be read as real occupied space.

### V3 decision and measurable improvement

V3 replaces that path with the renderer-neutral `catalogue-density` contract in
`apps/web/src/lib/spatial/galaxy-density.ts`:

- every cell has an integer grid address, actual cell size and origin, real
  centroid, and source-derived system count;
- response bounds, generation, pyramid version, level, coverage timestamp,
  completeness and source/covered counts are required;
- complete packets must reconcile the sum of cell counts to both covered and
  source-system counts;
- duplicate cells, invented/out-of-cell centroids and dishonest target counts
  are rejected; and
- the Babylon adapter creates geometry only for accepted cells. An absent or
  empty layer creates no substitute density mesh.

The Review Lab fixture contains 34 explicitly listed synthetic system positions.
Its deterministic fixture builder produces 20 occupied cells that reconcile
34/34. The word _synthetic_ applies to the test coordinates, not to generated
Galaxy structure: there is no random/noise/spiral occupancy path.

### Current comparative evidence

| Observable                | V2                                           | V3 slice 01                                                       |
| ------------------------- | -------------------------------------------- | ----------------------------------------------------------------- |
| Visible whole-Galaxy form | Procedural `VolumetricGalaxy` always mounted | Only accepted cell centroids create density instances             |
| Density meaning           | Ratings score and occupancy mixed            | Cell size is a bounded function of `systemCount` only             |
| Missing factual data      | Procedural Galaxy remains visible            | Zero density geometry; no generated replacement                   |
| Generation/coverage       | Not carried through the visible product      | Required and exposed in the Review Lab                            |
| Renderer proof            | Prop/mock and expression evidence            | Babylon `NullEngine` inspects real mesh/thin-instance output      |

**Disposition:** accepted as a truthful fixture kernel. It is not production
density. M3 must build and reconcile `v3_spatial.cell_summary`; M4 must connect
that published generation and prove 20k/40k LOD and ambient-off visual budgets.

## Galactic regions comparison

### V2 baseline and evidence quality

V2's `frontend/vite.authoritative-regions.ts` and
`frontend/src/features/map-foundation/authoritative-regions.ts` derive a static
resource from `apps/importer/src/data/region_map.json`. Retained evidence reports
42 labels, 42 unique non-zero IDs, 22,595 boundary segments, a 2,312,898-byte
resource, deterministic lookup fixtures and whole-grid reach checks. This is the
strong V2 pattern retained by V3.

V2 runtime validation did not require the exact ID/name sequence, pinned source
hash, all 2048 rows at decoded width 2048, or label-anchor/lookup agreement.
Regions were line/label context, not first-class hover/select/query targets, and
the boundary hierarchy could overpower stellar data.

### V3 decision and measurable improvement

`apps/web/src/lib/spatial/galaxy-regions.ts` and
`apps/web/vite.galaxy-regions.ts` improve the same audited source path by:

- requiring the exact 42 names in exact ID order and proving IDs 0–42 are
  present in the source grid;
- normalizing LF before verifying pinned SHA-256
  `910142d4deb510d80128509bf68cf3b8de8a2c45006d99d4233ee33d95321152`;
- requiring exactly 2048 rows, each decoding to exactly 2048 cells;
- deriving 22,595 boundary segments and 42 anchors deterministically in
  canonical V3 x/z coordinates with y=0;
- checking every anchor resolves through the RLE lookup to its own region and
  preserving unknown/out-of-source as `null`;
- enforcing a 25,000-boundary and 4 MiB asset budget; and
- failing build/dev resource emission if the source hash or provenance receipt
  differs.

Babylon renders the complete accepted boundary set as one bounded, non-pickable
line system and publishes the source hash and 42/42 render receipt. This is
deliberately a boundary slice: it does not yet claim projected labels, fills,
hover, picking or selection.

### Current comparative evidence

| Observable                    | V2                               | V3 slice 01                                                       |
| ----------------------------- | -------------------------------- | ----------------------------------------------------------------- |
| Canonical identity validation | Count/reach oriented             | Exact 42-name/ID contract plus pinned hash                        |
| Raster validation             | Deterministic derivation         | Every one of 2048 rows must decode to 2048 cells                  |
| Lookup/anchor agreement       | Partial fixture coverage         | All 42 anchors checked against matching RLE region                |
| Unknown space                 | Lookup support                   | Explicit `null`; no nearest-region assignment                     |
| Renderer proof                | Derived-resource/component tests | Actual Babylon line mesh and canonical y=0 positions inspected    |
| Interactivity                 | Camera-context lines/labels      | Not yet implemented; explicitly reported as zero pickable regions |

**Disposition:** accepted as the authoritative V3 boundary/lookup foundation,
not as complete M2 region UX. Fill/label LOD agreement, deterministic label
layout, hover/select/query, central picking, visual hierarchy and commercial
rights remain release gates.

## Evidence commands and limits

Current automated evidence:

- focused Vitest: five files, 20 tests passed;
- complete web Vitest: 25 files, 187 tests passed;
- `svelte-check`: zero errors and zero warnings;
- focused ESLint: passed;
- production Vite build: passed; derived region resource 3,128.63 kB before
  gzip, below the 4 MiB gate;
- Chrome Cypress Review Lab: accepted revision 2, both layer receipts, 42/42
  regions, 22,595 boundaries, ambient-off state and a non-background canvas
  pixel probe; and
- captured Review Lab and Babylon-map images in the configured 1280×720 Chrome
  lane (the headless browser's content capture is 1258×622).

The visual lane initially exposed a WebGPU-only black frame even though backend
startup and geometry receipts passed. The demand-render path omitted Babylon's
engine `beginFrame()`/`endFrame()` boundary, so WebGL appeared to work while
WebGPU commands were not submitted. Slice 01 now submits bounded warm-up frames
through the engine boundary and withholds `SCENE_APPLIED` until the ready frame
has been drawn. The canvas pixel probe protects that renderer-crossing failure.

The browser capture is deterministic fixture evidence, not physical-GPU,
WebGPU/WebGL2 equivalence, performance, accessibility or visual-design
acceptance. The existing region source remains non-commercial-only and requires
the documented rights decision before commercial deployment.

The production build still reports the existing over-500 kB chunk warning; the
Babylon client chunk is approximately 925 kB before gzip. Bundle splitting and
map-route loading remain M1/M2 performance work, not a waived gate.
